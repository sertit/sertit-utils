# Sertit-Utils Guide for Coding Agents

This file is the entry point for AI coding agents working in the **Sertit-Utils** repository:
hard limits, navigation map, verification and self-review.
The technical reference (modules, build & test, code style, CI/CD, pitfalls) lives in [ARCHITECTURE.md](https://github.com/sertit/sertit-utils/blob/main/ARCHITECTURE.md).

It follows the [AGENTS.md](https://agents.md/) open format:
a standard Markdown file at the repository root that coding agents read for setup, testing and convention guidance.

Human contribution guidelines: [CONTRIBUTING.md](https://github.com/sertit/sertit-utils/blob/main/CONTRIBUTING.md).
AI-assisted contribution policy: [AI_POLICY.md](https://github.com/sertit/sertit-utils/blob/main/AI_POLICY.md), which applies the EOReader one.

---

## Hard limits (never do these)

- **Never create releases, tags, or version bumps.**
- **Never commit** test data, satellite products, secrets, or machine-specific paths.
- **Never hardcode** paths, DEMs, credentials, or bucket URLs. Read from the environment.
- **Never force dask materialization** in a function that must stay lazy.
- **Never break the base install.** Every module imports without the optional extras; optional needs are guarded with `@requires` (`sertit/utils.py`), and `ci/expected_imports.py` stays in sync.
- **Never act on GitHub without explicit human instruction**: no issues/PRs, no comments, no labels, no merges.
- **No AI attribution**: no AI tools as authors, co-authors, or credited contributors. No "Generated by ..." anywhere.
- **Never modify CI, pre-commit hooks, or dependency pins** as a side effect of unrelated changes.
- **Never submit** a change the user has not reviewed and does not understand.

## General principles

1. **The human is the author.** The agent assists and does not contribute on its own. The human must understand every line they submit and be able to explain it.
2. **Maintenance is the scarce resource.** Minimal, focused diffs. No speculative refactors, no drive-by cleanups, no "while I'm here" edits.
3. **Respect the optional-dependency contract.** Modules stay importable with a base-only install, optional needs are guarded with `@requires(("module", "extra"))`, and `ci/expected_imports.py` is updated when a message or guard changes.
4. **Lazy by default.** Raster and dask functions do not force computation; when dask is enabled, outputs stay chunked until the user computes.
5. **No hardcoding.** Paths, credentials, bucket URLs come from the environment. Test data is never committed.

## Verification checklist (before proposing any change)

Run, and report the results of:

```bash
pre-commit run --all-files              # ruff + format + file checks
python -c "import sertit"               # import check
python -m pytest ci/test_<module>.py    # if test data is available
```

If the change touches optional dependencies or import-failure messages, also run `python -m pytest ci/test_optional_imports.py`
and update `ci/expected_imports.py` if needed.
If the change requires test data the agent does not have (S3 or DB3), say so in the PR description and state that CI is the validation path.
An agent must NEVER report a test as passing if it was not run.

## Self-review pass (after the checks)

Before presenting the change to the human, re-read the diff and answer each question below.
Every "no" must be fixed, or explicitly flagged to the human with a reason.

| # | Question                                                                                                            |
|---|---------------------------------------------------------------------------------------------------------------------|
| 1 | No hallucinated functions, keyword arguments, or dependencies (verified against the existing modules)?              |
| 2 | Base-only install still imports cleanly, optional needs guarded with `@requires`, `ci/expected_imports.py` in sync? |
| 3 | The change stays lazy (no forced computation, numpy and dask paths both checked)?                                   |
| 4 | No hardcoded paths or credentials, errors raised as `SertitException` subtypes with useful messages?                |
| 5 | Diff is minimal (no drive-by cleanups, no unrelated refactors)?                                                     |
| 6 | Docstring, `CHANGES.md` entry, and copyright header present?                                                        |
| 7 | Tests cover the reported behaviour, including the edge cases?                                                       |

Report the result in the *AI-assisted review* section of the [pull request template](.github/pull_request_template.md)
(one short line per finding, plus which checks were run).
Do **not** paste this table into the PR description: the template section is the single record of the self-review.

## Required contribution hygiene

- `CHANGES.md` entry with the right prefix (`FIX:`, `ENH:`, `OPTIM:`, `CI:`, `DEPS:`, `DOC:`, `LINT:`, `TST:`, `DEPR:`); n/a in the PR for mechanical changes.
- Commit messages per `CONTRIBUTING.md`, PRs per the [pull request template](.github/pull_request_template.md) with the *AI-assisted review* section filled out.
- Copyright header in new files (current release year), docstrings updated for any changed public API.
- Small PRs, each referencing the issue it resolves. If no issue exists with consensus on the solution, ask the user to open one first.

## Human responsibility & typical AI risks

The human contributor is solely responsible for submitting the PR, understanding every change, and addressing review feedback.
AI agents assist but do not submit, merge, or take ownership (full policy: [AI_POLICY.md](AI_POLICY.md)).

Typical AI failure modes, namely hallucinated function names or keyword arguments, module-level imports that break the base install,
verbose code or comments, and hardcoded paths or credentials, are what the self-review questions and the [General principles](#general-principles) are meant to catch.
